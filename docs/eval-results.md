# 評測結果（2026-07-22 實測）

本輪全部實測數據與判讀。**逐次原始值都列出來，不只中位數**——變異數才是誠實的部分。

總花費約 **$1.6**、約 25 分鐘。

## 為什麼分三層

一個常見的誤解是「評測就是測模型能力」。SWE-bench 這類基準測的是 **模型 × harness 的乘積**，
從單一個分數**沒辦法分離兩者的貢獻**——這也是 SWE-agent／Agentless 那些論文在比 scaffold 而非比模型的原因。

本專案的三層各有分工：

| 層 | 測什麼 | 模型的角色 | 成本 |
|---|---|---|---|
| ① 檢索 `hit@k` | **純 harness** | **完全不參與** | $0 |
| ② A/B 消融 | **harness 的邊際貢獻** | 固定，當背景 | 幾分錢 |
| ③ SWE-bench | 模型 × harness | 混在一起，分不開 | $0.24/題 |

**①② 用來評自己的機制，③ 只當外部座標。**

## ① 檢索評測：hit@k / MRR（$0、12 秒、無 LLM）

```bash
go run ./cmd/ingest -root internal/eval/testdata/mem_multihop \
  -eval internal/eval/testdata/mem_multihop/labels.jsonl -k 3 -hops 1
```

語料：12 個互連服務節點（`testdata/mem_multihop/.claw/memory/`），12 題標註，半數多跳。

> **2026-08-05 更新：embedding 模式補跑完成**（bge-m3 / Ollama）。先前那列 N=0 被整個跳過，
> 「三模式對照」名不副實；現在三個模式都有數字了。

```
模式                  N    hit@k      MRR
keyword            12     0.50     0.50
embedding          12     0.58     0.53     ← 補跑（bge-m3），先前 N=0
keyword+kg         12     1.00     0.69
```

前置：`go run ./cmd/ingest -root <語料> -embed` 建向量快取（需 `COGITO_EMBED_MODEL` + 端點）。

**多跳題的答案節點與查詢字面零重疊**，keyword 在設計上就撈不到（Seeds 只回 score>0），
只有沿 `[[link]]` 擴張的 KG 撈得到。

**補跑 embedding 回答了一個原本無法反駁的質疑**：

> 「你們的 KG 贏 keyword，但**換成向量檢索不就解決了嗎**？」

**不能。** embedding 只到 **0.58**，離 keyword+kg 的 1.00 還很遠——它比 keyword（0.50）
只好一點點。原因就是這份語料的設計：多跳題的答案節點**跟查詢在語意上也不像**，
它只是【被連到】像的那個。向量相似度走不了 A→B→C 這條路，那是圖的工作。

> 換句話說，**贏的是「沿關係擴張」這個機制本身，不是「比 keyword 更好的相似度函數」**。
> 這是這輪補樣本最有價值的一條——先前 N=0 時，這個質疑完全無法回答。

**防作弊護欄**（`memeval_test.go`）：

```go
if kw >= 1.0 { // keyword 若滿分表示語料沒真正考多跳
    t.Errorf("keyword 不該滿分（多跳題應漏），got %.2f", kw)
}
```

若有人把語料改簡單到 keyword 也能撈到，測試會失敗。這讓「0.50 vs 1.00」不會因語料退化變成假勝利。

## ③ 技能 A/B ×20（`cmd/bench -skill-ab -ab-n 20`，模型 claude-haiku-4-5）

> **2026-08-05 更新：n 從 5 補到 20，結論改變。** 舊的 n=5（1/5→4/5、p=0.206）只能當觀察；
> 補到 n=20 後 **p=0.0248 達顯著**，可以當結論了。舊資料保留在文末的摺疊區。

情境刻意設計成**模型無法從程式碼推得**的專案慣例（升版本號要同時改 `package.json` 與 `VERSION` 且一致）。

| | OFF | ON |
|---|---|---|
| 通過率 | **7/20（35%）** | **15/20（75%）** |
| 回合中位數 | 4 | 4 |
| 成本中位數 | $0.0145 | $0.0159（**+9.7%**） |

**Fisher 精確檢定雙尾 p = 0.0248 → 達顯著（α=0.05）。**
本輪總花費 $0.6520、耗時約 4.5 分鐘。逐次原始數據見下方摺疊區（JSON 原檔留在本機
`bench-reports/`，該目錄已 gitignore；要複現直接重跑指令即可）。
顯著性由 `internal/eval/abstats.go` 計算（先前的 p=0.206 是手算的，程式裡沒有）。

**判讀：技能改善正確性，代價比原本以為的小很多。** 通過率 35%→75%，成本只多 9.7%
（不是 n=5 時看到的 +35%），回合中位數**完全沒變**。

**n=5 的三個數字全部被高估了**——這是這輪最有價值的發現：

| | n=5 的說法 | n=20 的實況 | 差異 |
|---|---|---|---|
| OFF 通過率 | 1/5（20%） | 7/20（35%） | 低估了 baseline |
| ON 通過率 | 4/5（80%） | 15/20（75%） | 高估了效果 |
| 回合中位數 | 4 → 5（+1） | 4 → 4（**+0**） | 這個觀察**消失了** |
| 成本中位數 | +35% | **+9.7%** | 高估約 3.6 倍 |

效應方向撐住了，但**每一個幅度估計都縮水**。「多花一個回合載入正文」那句因果解釋在 n=20
下不成立——ON 側 20 次裡有 13 次仍是 4 回合。

**反例仍存在但不推翻結論**：2 次「無技能通過、有技能失敗」。這是機率性改善的正常樣貌，
不是穩定因果——p 值已經把這件事計入。

## 方法論：本輪犯過的錯（值得記住）

**① n=1 得出的結論兩次都是錯的**

第一次跑 A/B（各一次）得到「記憶有效、技能無效」。跑到 n=5 才發現技能**其實改善通過率**（1/5→4/5），
只是我盯著回合數與成本看——那是 mem-ab 表格強調的欄位，我順手套用到 skill-ab，**看錯了指標**。

教訓：不同機制改善的維度不同，**先想清楚該看哪個指標**再讀數字。

**② 差點只重測不利的結果**

發現 skill-ab 沒效果後，第一反應是「再跑 5 次確認」——但當時並沒有打算重跑 mem-ab。
那正是「不喜歡的結果就多測幾次，喜歡的就收下」的偏誤。**兩邊都跑到 n=5 才對稱。**

**③ 與既有設計的落差**

`evolve.MinVerifySamples = 10` 已經為調參驗證設了樣本門檻，但 **A/B 這邊沒有同樣的門檻**——
`cmd/bench -mem-ab` 跑一次就給結論。這是真的方法論缺口，未修。
